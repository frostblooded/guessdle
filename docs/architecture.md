# Architecture

Reference for working on `src/`. Decisions: `docs/adr/`. Terms: `GLOSSARY.md`.

## Client

- `src/` holds ES modules (imports use `.ts`/`.tsx` extensions). The front-end is one React app (ADR 0018): `index.html` loads `src/main.tsx`, which mounts `src/App.tsx` (React Router routes, TanStack Query client). Vite builds it into `dist/` with hashed files under `/dist/assets/` (ADR 0017). The pure modules (`date`, `game`, `game-state`, `play`, `correctness`, `slug`, `theme`, `login-logic`) are unit-tested by importing the `.ts` directly in Vitest, so keep them erasable-syntax only (no `enum`) (ADR 0004).
- Routes (clean URLs, `src/routes/`): `/` the gallery (`gallery-page.tsx`: `GET /api/games`, Petdle first and full-width, then approved playable games newest first; each card footer names the game type through `src/components/game-kind.tsx`, whose `KIND_LABELS` gives every kind its label and icon), `/g/<slug>` Play (`play/play-page.tsx`; the shell is served by the API (`src/server/routes/shell.ts`): title, description and `og:*` (cover as `og:image`) injected from the database, HTML-escaped, `no-cache`, `noindex` for non-approved games; a draft, under-2-entry or unknown game gets HTTP 404 with the same shell, and the app draws the not-found state; nginx proxies `/g/<slug>` to the API, the dev server falls back to the static shell without a database), `/g/<slug>/days` (the Past days list, `play/days-page.tsx`) and `/g/<slug>/day/<n>` (a Past Day on the Play page), `/create`, `/my-games` and `/settings` (signed in; `settings-page.tsx`, the approval and friend request email switches), `/friends` (signed in; see Friends below), `/g/<slug>/edit` (the editor, `edit/`, see ADR 0015), `/how-to-play`, `/login`, `/verify` (the emailed link: verifies the token, then goes to Play or explains the failure), `/admin` (`admin/`; client-side 401/403 gate, the API enforces the real check), `/party` and `/party/<CODE>` (`party/`, party mode, see Party below), `/profile`, `/u/<username>`, `/p/<id>` and `/p/<id>/edit` (`playlists/`, see Playlists below). Any other path renders `not-found-page.tsx`, and the servers answer it with status 404 (`ROUTES` in `scripts/server.mjs`, `deploy/nginx.conf`). `src/components/layout.tsx` renders the header (brand, nav, theme button, Sign in / account menu) and footer around every route; the signed-in user is the shared `useMe()` query (`src/lib/api.ts`). Pure sign-in logic (messages, email shape, resend cooldown) is `src/login-logic.ts`.
- The design system is Tailwind CSS v4 with tokens in `src/styles.css` (`@theme inline`); light and dark are one `light-dark()` hex value per token, and the theme button only flips `color-scheme`. Shared components (button, card, input, alert, badge, tabs, table, alert dialog) are shadcn/ui-style in `src/components/ui/`, on Radix primitives.
- Storybook (`npm run storybook`, config in `.storybook/`) shows the UI components and the play pieces (board, guess box, result banner) in light and dark; stories sit next to their component as `*.stories.tsx` and are type-checked and linted with `src/`.
- `src/game/game.ts` holds the pure guess judging (`gradeIds`); the guess box is a Downshift combobox (`src/routes/play/guess-box.tsx`); `src/components/board.tsx` draws the board rows shared by Play and How to play; `src/components/theme-button.tsx` drives the theme (`src/theme.ts`).
- The roster lives in Postgres (`games`, `attributes`, `entries`, `entry_values`; migration `005_games.sql` moved Petdle in as game `petdle`). `GET /api/games/:slug` gives the page the game's attributes and active entries (`id`, `name`, `photo`); the board columns are Name, then the game's attributes in order (`boardColumns` in `src/game/game.ts`). Guesses are numeric entry ids. Service seam: `src/server/games.ts` (`findGame`, `loadRoster`).
  - Image attributes (migration `014_image_attributes.sql`). An Image value is one upload URL in `entry_values`; it may stay blank (it never pauses a game) and is never graded: its cell shows the picture, marked correct only on the answer itself so a winning row stays all correct, and party squares skip it. An entry's `photo` in player payloads is its first non-blank Image value (`firstImage`); the gallery collage uses the same. Migration 014 moved each classic entry's old built-in photo (`entries.photo_url`, now Blur-only) into an Image attribute named Photo, first in each classic game's order.
  - Attribute types: Text (exact match), List (same set correct, shared value partially correct) and Number (`gradeNumber`: same value correct, otherwise a `hint` of higher or lower on the graded cell, drawn as an arrow by `board.tsx`; values parsed by `src/game/number.ts`, migration `008_number_attributes.sql`); grades are never stored (ADR 0013).
  - Every attribute is required: `saveEntry` refuses `missing_values` (and `not_a_number`). A game with an active entry missing a value is paused (`Roster.incomplete`, SQL `HAS_MISSING_VALUES` in `games.ts`): `GET /api/games/:slug` says `paused`, `openDay` (`play-day.ts`) refuses it with 409 `game_paused`, parties refuse it, submit answers `incomplete_entries`, the gallery leaves it out. `playBlocker` in `access.ts` is the one rule for too few entries or paused; play, opening a party, starting a round and submit all ask it (the gallery's SQL is its only other copy).
  - The editor's Attributes tab keeps edits locally until Save, which sends the whole list to `PUT /api/games/:slug/attributes` (`saveAttributes`: one transaction, list order is column order). Removing an attribute or changing its type erases its values (also on the single-attribute `PATCH`/`DELETE`).
- Blur games (ADR 0019, migration `010_blur_games.sql`): `games.kind` is `classic` or `blur` (picked on `/create`, never changed); a Blur game has no attributes, `games.blur_tries` (1-9) tries, and each entry a square photo plus `entries.blur_order` (cells 0-8, first cleared first). Pure rules in `src/game/blur.ts` (`isBlurOrder`, `toggleCell`, `blurProgress`, `cellRect`). The editor picks the order with `src/routes/edit/blur-order-editor.tsx`; `saveEntry` refuses `missing_order`. Rows are the name only (`gradeIds(..., "blur")`): the grade, state and party code mark `lost` after the last try and reveal `answer` plus `answerPhoto` once over. Player-facing payloads carry no Blur photos; boards are rendered by `src/server/routes/blur.ts` (`blurRenderer`: blurred image with the first n squares pasted back, WebP, `no-store`). Play and party rounds draw `src/components/blur-view.tsx`. Its gallery collage is blurred tiles (`tileUrl`, `tileRenderer`); a Sequence game's collage is each entry's first photo through the same tile route, unblurred, and a Quiz game's is its question pictures. Skips are `SKIP` in guess lists (`skippedRow`, `GuessForm`/`SkipButton`), stored with a null `entry_id`.
- Quiz games (ADR 0021, migration `022_quiz_games.sql`): `games.kind` `quiz`; each question is an entry (text in `name`, optional `photo_url`) with its answer in `entries.quiz`. Pure rules in `src/game/quiz.ts` (`parseQuizSpec`, `scoreAnswer`, `gradeQuiz`, `spreadOf`, party helpers). The editor's Questions tab is `src/routes/edit/questions-panel.tsx` (entry routes with `quiz`; `saveEntry` refuses `missing_answer`); no attributes, answers or skip period. `GET /api/games/:slug` sends `questions` without answers and no entries; every day route answers 404 (`openDay`). `POST /api/games/:slug/quiz` (`src/server/routes/quiz.ts`, storage `src/server/quiz.ts`) grades all answers, keeps the player's first score in `quiz_results` and returns the review and spread; Play draws `src/routes/play/quiz-play.tsx`. Party rounds are one question each in order (`party_quiz_answers`, socket message `answer`, `QuizRound` on `RoundData`, `src/routes/party/quiz-round.tsx`); a live round hides correctness. The party view is built in `src/game/party-view.ts`.
- Sequence games (ADR 0020, migration `021_sequence_games.sql`): `games.kind` `sequence`, no attributes, `games.blur_tries` is the photos per entry (default `DEFAULT_SHOTS`), each entry's 16:9 photos in `entries.shots` ("" for an empty slot; upload kind `shot`). `isImageGame` covers what Blur and Sequence share (name-only rows, tries, skips, hidden photos). Only entries with every photo (`hasAllShots`, `Roster.answerIds`) are drawn or scheduled; the game pauses only while none has them (`src/server/completeness.ts`). Unscheduled days take the lowest never-used id, else a draw outside the skip period, never an entry scheduled later (`drawSequenceAnswer` in `src/server/answers.ts`); entry and photo-count edits call `rescheduleFuture`. Photos reach players only through `GET /api/games/:slug/shot/:n` and `/api/parties/:code/shot/:round/:n` (`src/server/routes/blur.ts`); Play and party rounds draw `src/components/sequence-view.tsx`, the editor `src/routes/edit/shots-editor.tsx`.
- How to play (`how-to-play-page.tsx`, `how-to-play/`) is a practice game on a frozen copy of Petdle: migration `015_tutorial.sql` copied its active pets and values once into the one-row `tutorial` table (view `tutorial_photos` lists its photo URLs for upload references), served by `GET /api/tutorial` (`src/server/routes/tutorial.ts`). Later Petdle edits never change it. Ati is the secret; the browser grades with `gradeGuess`, and `src/game/tutorial.ts` explains each clue (`explainRow`) and fades pets that no longer fit (`stillFitting`). The page is an accordion, one item per game kind with Classic open; Blur and Sequence practice rounds (`picture-practice.tsx`) reuse `BlurView` and `SequenceView` on a pet photo (covered squares drawn over it, zoom steps for the photos), and the Quiz round (`quiz-practice.tsx`) asks three questions built from the pets and checks each answer right away.
- Cell result classes: `correct` / `partially-correct` (arrays sharing an element) / `incorrect`, styled in `src/styles.css`.

## Daily Answer

Stored server-side per game (`daily_answers` keyed by game and date, `src/server/answers.ts`), never in the bundle (ADR 0008, 0010). Day 0 is the game's `start_date`.

- Drawn at random on the first request of a day. All missing days fill in order under an advisory lock, skipping the previous Skip Period answers (the game's `skip_period`, default 5, clamped to N-1).
- "Today" is the date in `SERVER_TIMEZONE` (default Europe/Sofia). Roster changes no longer rewrite past days.
- Migration `db/migrations/001_daily_answers.sql` backfills days 0..2026-10-16 from `db/backfill/answers.json`.

## Play

- Anonymous (`createPlay`, `src/game/play.ts`): entry ids live in `localStorage` under `game:<slug>:` keys (`createGameState`, `src/game/game-state.ts`: a missing or other-day `lastPlayed`, or a newer server `day`, clears them; blocked storage falls back to memory; the old un-prefixed keys are wiped once at start-up (`src/main.tsx`), which shows a dismissible notice that the browser guesses were reset; signing out clears every `game:*` key). `POST /api/games/:slug/grade {ids}` returns `{day, rows, victory, answer?}`, `answer` only on victory. `POST /api/games/:slug/give-up` is stateless and open to anyone by decision. Every response carries the Day Number; a client seeing a newer day resets itself (`onNewDay`).
- Signed in: email magic link (`src/server/email-login.ts`, `mailer.ts`, ADR 0011; the mail links to `${PUBLIC_URL}/verify?token=...`; client `src/routes/login-page.tsx`, `src/routes/verify-page.tsx`), Postgres sessions (`src/server/auth.ts`). `GET /api/games/:slug/state` and `POST /api/games/:slug/state/guess|give-up|merge|reset` store ids per user and day (`src/server/user-game.ts`, client `src/game/server-play.ts`); victory is derived on read. `merge` adopts leftover anonymous guesses on login (`src/game/merge.ts`).
- Day of play (`src/server/play-day.ts`): `openDay` turns a game and the `?day=` query into a `PlayDay` (date, Day Number, past, the drawn answer) or a refusal (`no_such_day`, `not_enough_entries`, `game_paused`, `answer_missing`); `boardOf` grades a guess list against it and says lost and what the finished day reveals; `recordWin` records a first win and returns the day's stats. Routes only parse the request and map the outcome to HTTP (`playDayOf` and `sendRefusal` in `routes/context.ts`); `user-game.ts` stores a signed-in player's guesses on top of a `PlayDay`.
- Past days (`GLOSSARY.md` Past Day): the grade, give-up, `/result` and `/state*` routes take `?day=N` (0 up to today; anything else is 404 `no_such_day`, `dayOf` in `src/server/play-day.ts`), and `GameContext.past` marks an archive day; its first win counts in that day's stats like an on-the-day win; `/state/merge` refuses a past day (`stale_day`). `GET /api/games/:slug` carries `today` and `startDate`; `GET /api/games/:slug/days` lists every day newest first with the signed-in player's status (`src/server/days.ts`; anonymous statuses come from the browser through `readProgress` in `game-state.ts`, which writes nothing) and a Blur game's `tries`; `statusOf` in `src/game/days.ts` calls a day won, gave-up, lost (every Blur try used, `outOfTries` in `blur.ts`, the same rule as solo play and party rounds), playing or unplayed. The client picks where a day's game lives in `src/game/open-play.ts`, and `src/routes/play/use-play-board.ts` runs the board session on top of it (opening the Play, then each guess, give-up and reset with the result, notice and Free Hint they leave); an anonymous Past Day keeps its state under `game:<slug>:day:<n>:` keys (`pastDayStorage`), which never expire. The victory clock of a Past Day lives under its own keys too.
- Free Hints and descriptions (migration `018_free_hints.sql`): `entries.description` is optional text edited on the Entries tab for every kind; `revealOf` (`play-day.ts`) sends it as `answerDescription` with the answer once the day is over, and party rounds as `answer.description`. Pure hint rules in `src/game/free-hint.ts` (`hintChoices`, which `boardOf` returns as `hints`: offered after `FREE_HINT_AFTER` (3) graded rows to a classic game not won while some attribute is unmatched; the description is never a hint (migration `023_attribute_hints_only.sql` dropped description hints); `pickHint` draws an unmatched attribute with the app's `random`; `revealHint` reads the value from the answer). Anonymous: the grade response carries `hints`, `POST /api/games/:slug/hint {ids, kind}` is stateless like give-up, and the browser keeps the hint under `game:<slug>:hint`. Signed in: `user_hints` (one per user, game and day; `POST /state/hint {kind}`, cleared by reset), and the state view carries `hint` or `hints`. Party: the `hint` socket message stores a `party_hints` row; `partyView` gives the viewer `yours.hint` or `yours.hints`. Both pages draw `src/routes/play/free-hint.tsx`.
- Playlists (`GLOSSARY.md` Username, Playlist): `users.username` and the `playlists` / `playlist_games` tables (migration 012, `src/server/playlists.ts`, routes `src/server/routes/playlists.ts`). `PUT /api/me/username` sets it once; `GET /api/users/:username` is a Profile (public playlists, or all for the owner, plus the owner's gallery games); `GET|PATCH|DELETE /api/playlists/:id` (a private one is a 404 to others, PATCH `games` replaces the order), `PUT|DELETE /api/playlists/:id/games/:slug` and `GET /api/my-playlists?game=<slug>` back the Save button (`src/components/save-to-playlist.tsx`) on gallery cards, profile and playlist cards (`src/components/game-card.tsx`) and Play. Games are filtered with the gallery's rule (`listGallery` with a scope, `src/server/gallery.ts`) on every read, so a hidden game stays stored but unseen. Cached profile, playlist and Save-menu queries are invalidated after every change (`src/lib/playlists.ts`).
- Victory stats: a win opens a popup (`src/routes/play/stats-dialog.tsx`, state in `use-victory-stats.ts`) with the guess count, the time since the board's first guess (`game:<slug>:firstGuessAt`, or the Past Day's keys, in the browser; unknown when another device made it) and two bar charts of the day's winners. `POST /api/games/:slug/result {ids, seconds, player}` records the player's first win of the day in `game_results` (`src/server/results.ts`; `user:<id>` from the session and its stored guesses, else `anon:<token>` from the browser's `guessdle:player` token and the sent ids, which must end with the answer) and returns the day's stats (`summarize`, `src/game/stats.ts`). Only the first attempt of the day counts: a give-up or a Blur game's used-up tries record a failed row (`recordFailure`; signed in from `giveUp`, `addGuess` and `mergeLocal`, anonymous from `/give-up` and `/grade` when the body carries the browser's token), so a win after a reset shows the popup with `firstTryFailed` and no score. A replay after a reset changes nothing; "See stats" reopens the popup.
- A draft game, or one with fewer than 2 active entries, is a 404 except to its owner and admins. `src/server/access.ts` owns that rule and the 404, 401, 403 order: `resolveGame(pool, now, req, slug, need)` with `need` = `play` | `edit` | `admin` (pure core `decide`; `resolveAdmin` for admin routes without a game). The shell, `loadGame` (play), `guardGame` (`routes/context.ts`, used by manage, answers and admin routes) all go through it, so a hidden game is a 404 before any 401/403. Signed-in game-state routes (`routes/game.ts`) still check the session first.
- Failure codes: `src/game/failures.ts` is the one table of code to HTTP status and client text (`FAILURES`, `failureText`); routes send them with `fail(res, code)` (`routes/context.ts`), `manage-client.ts` shows the text. Add a code there only.
- Limits: `src/game/limits.ts` holds every size limit (name 60, description 500, slug 3-40, attribute name 40, value 200 x 20 items, `MIN_ENTRIES`). The fields' `maxLength` values and `RESERVED_SLUGS` (every top-level page, folder and route) are tied to them by `tests/limits.test.ts`.
- Routes live in `src/server/routes/` (`auth`, `game`, `answers`, `admin`), each taking one `AppContext`.

## Admin

`/api/admin/users|backup|queue|games` and the `/admin` page (`src/routes/admin/`, tabs Users, Backups, Approval queue, All games). Answers peek/override is per game, owner or admin, in the editor's Answers tab (`src/routes/edit/answers-panel.tsx`; Answer History from a week back, real dates) over `/api/games/:slug/answers`: peek and override answers (today or future only; later generated days are re-drawn). An override or a cleared override that changes a stored day's entry restarts that day for everyone (`restartIfChanged`): its guesses, give-ups and results are deleted and `daily_answers.revision` goes up; grade, give-up and state responses carry the revision, so browsers drop a board played on an older one and say so, and a merge of one is refused. The editor confirms before changing today's answer. Changing a game's skip period (0..N-1) re-draws its future generated days only (`redrawFuture`). Admin also: promote or demote users (no self or last-admin demotion, no promoting a banned player), show backup age.

Friends (`GLOSSARY.md` Friend; `friendships`, migration 026, `src/server/friends.ts`, routes `src/server/routes/friends.ts`, page `src/routes/friends-page.tsx`): one row per pair, pending until `accepted_at` is set. `POST /api/friends {query}` finds the other by exact username or exact email (any case; no partial search, so emails cannot be browsed), and accepts instead when they had already asked; it mails the other (`mailRequest`) unless `users.mail_friend_requests` (a Settings switch) is off. `PUT /api/friends/:id` accepts, `DELETE` declines, cancels or unfriends. `/api/me` sends `friendRequests` for the account menu's badge. `dayStats` and `recordScore` add `friends` (signed-in players only): accepted, unbanned friends' first tries of that day (or first quiz scores), wins first; the stats popup and the quiz result show them through `src/components/friend-results.tsx`. Banned players cannot send requests and cannot be found.

Bans (`GLOSSARY.md` Ban; `users.banned_at`, `ban_reason`, migration 019): `PUT /api/admin/users/:id/ban {reason}` and `DELETE` to unban (`setBan` in `src/server/users.ts`; never oneself or an admin). Nothing else is written, so an unban restores everything. `GameRow.ownerBanned` makes `access.ts` treat the game as hidden (404) to all but its owner and admins, and `canManage` refuses the banned owner with 403 `banned`; creating games, uploads and playlist writes refuse it too. The gallery rule (`IN_GALLERY` and `listGallery` in `src/server/gallery.ts`, SQL `OWNER_BANNED`) leaves their games out of the gallery, profiles and playlists; `findPlaylist` and `loadProfile` hide their playlists from all but them and admins; `dayStats` drops their wins except from their own view. `/api/me` sends `banned` and `banReason` for the banner in `layout.tsx`.

## Approval

`src/server/game-edits.ts` (`gameEdits`) is how an owner or admin edits a game: attributes, save or delete an entry, patch the details, drop, move. Each edit bundles what it sets off: the upload check (`mayAttach`), the game lock and status rule (`lifecycle.edit`), the Daily Answers it changes (deleting an entry runs `releaseEntry`, a new skip period `redrawFuture`, both in the edit's own transaction, under the game row lock and then the answer lock) and freeing replaced uploads. `routes/manage.ts` only parses requests and maps outcomes.

`src/server/lifecycle.ts` owns every status change (edit kinds that reset approved/rejected, submit, unpublish, approve, reject; a Save that only reorders attributes, or only changes a Quiz question's right answer or number range, is not an edit and keeps the status) and `src/server/approval.ts` the admin queue and game list (game delete is `uploadRefs(...).dropGame`): `POST /api/games/:slug/submit` (draft or rejected, 2+ active entries, 409 `too_few_entries` / `invalid_state`) and `/unpublish` (approved) are owner/admin; `/api/admin/queue` (pending, oldest first), `POST /api/admin/games/:slug/approve|reject` (reject needs a reason, max 500) and `DELETE /api/admin/games/:slug` are admin only (Queue tab, `src/routes/admin/queue-panel.tsx`). `/api/me` gives admins `pending`, shown on the Admin link. The Play page shows the status line (`statusNotice`, `src/routes/play/play-status.tsx`) only to the owner and admins, since `GET /api/games/:slug` sends `status` and `rejectReason` only to them; its `canApprove` (`access.ts`: admin and pending) shows an Approve button that calls the same admin approve route, then refetches the `["me"]` query so the Admin link count updates. Every transition into pending (submit, unpublish, an edit resetting approved/rejected) sets `games.admin_mail_at` 5 minutes ahead (`gameLifecycle` in `lifecycle.ts`; routes pass an edit kind and cannot skip it); approving or rejecting clears it. `mailDueAdmins`, run every minute by `src/server/main.ts` and `scripts/server.mjs`, mails all admins through the `Mailer` about each game still pending past that time, so a game decided within 5 minutes sends no admin email and a restart loses none. Pure request validators are in `src/server/validate.ts`, the shared game transaction in `src/server/tx.ts`; edits of drafts or already-pending games do not, and a mail failure never fails the edit. The same place mails the game's owner (`src/server/owner-mail.ts`) when an admin approves or rejects it (with the reason) and when an edit sends an approved game back to pending; submit and unpublish do not. Each mail links to `/settings`, where `GET`/`PUT /api/settings/mail` (`src/server/routes/settings.ts`) read and save the owner's switches (`users.mail_approval` stops all, then `mail_approved`, `mail_rejected`, `mail_review`; all on by default; `src/mail-settings.ts`). Approving saves the game in `games.approved_snapshot`; `GET /api/admin/games/:slug/changes` lists what changed since then, shown by the See changes button next to Approve and Reject (`src/components/changes-dialog.tsx`, ADR 0022).

## Uploads

Before upload the edit page crops each pick in a Cropper.js dialog (issue #82): photos square, covers 16:7 (`UPLOAD_SHAPES` in `src/game/crop.ts`, which also holds the sizes and 5 MB limit the server uses). `src/image-cropper.ts` is the framework-free core (decode, mount, crop to a WebP or JPEG under the limit); `src/components/crop-dialog.tsx` is the React dialog around it (`useCrop`). Undecodable files never reach the server. Play shows photos square (`object-fit: cover`), so older uncropped ones still line up.

`POST /api/uploads?kind=photo|cover` (signed in, raw bytes as `application/octet-stream`, 5 MB) runs `src/server/images.ts`: type by magic bytes (JPEG, PNG, WebP), sharp resize (photo 800px, cover 1200px), WebP re-encode, random-hex name in `UPLOADS_DIR` (default `./uploads`); answers `{url: "/uploads/<hex>.webp"}` or 413 `too_large`, 415 `unsupported`, 422 `corrupt`. Prod: the `uploads` named volume is rw for `api`, ro for nginx (`/uploads/`, `/api/uploads` body cap 5m). The dev server serves the same folder. Petdle's own photos were moved here once by `scripts/import-photos.mjs <photos dir> <owner email> [cover]` (`src/server/import-photos.ts`, now on Petdle's Image values; rerunnable, skips values already moved); `howto/` holds three example photos for Storybook stories. Hygiene (table `uploads`): per-user rate limit (60/hour, `uploadLimit`) and byte quota (200 MB, 403 `quota_exceeded`, `src/server/upload-store.ts`). `src/server/upload-refs.ts` (`uploadRefs(pool, dir)`) owns upload references: `mayAttach(url, current, actorId, ownerId)` (clear, keep, or a file stored for the actor or the game's owner), `release(urls)` (deletes file and quota row unless a cover, a Blur entry's photo, an Image value (soft-deleted entries too) or a tutorial picture still uses it), `dropGame(game)`, `dropUser(id)` (delete, then release what they owned or used) and `sweep(now)` (`main.ts` at start and every 24h; files older than 1 day that nothing references). Routes never unlink files themselves; extend its reference queries when another table stores upload URLs.

## Party mode

ADR 0016. Pure rules in `src/game/party.ts` (codes, nicknames, ranking, Placement Points, socket message parsing; the per-viewer `partyView` in `src/game/party-view.ts`); storage in `src/server/parties.ts` (tables from `007_parties.sql`, `sweepParties` hourly from `main.ts` and on every read of one party), actions in `src/server/party-actions.ts` (under the party row lock), the socket hub in `src/server/party-hub.ts` (`attachPartySockets(server, app)` in `app.ts` hooks it to the HTTP server; `main.ts`, `scripts/server.mjs` and the party integration test call it). HTTP: `POST /api/games/:slug/parties {nickname}` (signed in, play access) → `{code, token}`; `GET /api/parties/:code` (visitor view, also the results page); `POST /api/parties/:code/join {nickname}` → `{token}`. Socket: `/api/parties/:code/socket`, first message `hello` with the token. Client: `src/routes/party/` (`party-page.tsx` picks `/party`, `/party?host=<slug>` or `/party/<CODE>`; `party-room.tsx` the live party, `standings.tsx` the scoreboard, podium and finished rounds, `tokens.ts` the stored player token), `src/party-socket.ts` (reconnects); the guess box and rows are Play's (`guess-box.tsx`, `src/components/board.tsx`). Play shows "Host a party" on any playable game.

## Server

- Rate limits: nginx and `src/server/rate-limit.ts`. `/api/test/login` exists only with `NODE_ENV=test`.
- Migrations: `db/migrations/*.sql`, applied at startup.
- Deploy, env keys, backups: `docs/deploy.md`.
- Site icon: `icons/favicon.svg` is the source (four result tiles, the last a `?`). `npm run icons` (`scripts/build-icons.mjs`, Playwright) renders `favicon.ico` (16/32/48) and `icons/apple-touch-icon.png`; commit all three. `index.html` links them, so Vite hashes them into `dist/assets/`; the root `favicon.ico` is also served for browsers that ask for it directly.

## Tests

- Unit, component and integration tests run on Vitest (`vitest.config.ts`: a `unit` project for `tests/*.test.ts`, a `ui` project for React components in `tests/ui/*.test.tsx` (jsdom, Testing Library; `npm test` runs both) and an `integration` project whose files run in parallel). `npm test` type-checks them all first with `tsc -p tsconfig.test.json`. Assertions use `node:assert/strict`.
- `npm run test:integration` runs the HTTP API against Testcontainers Postgres (needs Docker): `tests/integration/global-setup.ts` starts one container per run and `startDb()` gives each file its own empty database in it.
- Page URLs are served by `scripts/server.mjs` (dev) and `location /` `try_files` in `deploy/nginx.conf` (prod); `tests/e2e/server.spec.ts` and `tests/build-wiring.test.ts` cover both lists.
- `npm run test:e2e` starts a Testcontainers Postgres and Mailpit via `tests/e2e/serve.ts` (needs Docker); sign-in mail is read back through Mailpit's API. One integration test delivers through real nodemailer to Mailpit. The Daily Answer is random there; tests learn it through the API.
