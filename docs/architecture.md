# Architecture

Reference for working on `src/`. Decisions: `docs/adr/`. Terms: `CONTEXT.md`.

## Client

- `src/` holds ES modules (imports use `.ts`/`.tsx` extensions). The front-end is one React app (ADR 0017): `index.html` loads `src/main.tsx`, which mounts `src/App.tsx` (React Router routes, TanStack Query client). Vite builds it into `dist/` with hashed files under `/dist/assets/` (ADR 0016). The pure modules (`date`, `game`, `game-state`, `play`, `correctness`, `slug`, `theme`, `login-logic`) are unit-tested by importing the `.ts` directly in Vitest, so keep them erasable-syntax only (no `enum`) (ADR 0004).
- Routes (clean URLs, `src/routes/`): `/` the gallery (`gallery-page.tsx`: `GET /api/games`, Petdle first and full-width, then approved playable games newest first), `/g/<slug>` Play (`play/play-page.tsx`; the shell is served by the API (`src/server/routes/shell.ts`): title, description and `og:*` (cover as `og:image`) injected from the database, HTML-escaped, `no-cache`, `noindex` for non-approved games; a draft, under-2-entry or unknown game gets HTTP 404 with the same shell, and the app draws the not-found state; nginx proxies `/g/<slug>` to the API, the dev server falls back to the static shell without a database), `/create` and `/my-games` (signed in), `/g/<slug>/edit` (the editor, `edit/`, see ADR 0015), `/how-to-play`, `/login`, `/verify` (the emailed link: verifies the token, then goes to Play or explains the failure), `/admin` (`admin/`; client-side 401/403 gate, the API enforces the real check). Any other path renders `not-found-page.tsx`, and the servers answer it with status 404 (`ROUTES` in `scripts/server.mjs`, `deploy/nginx.conf`). `src/components/layout.tsx` renders the header (brand, nav, theme button, Sign in / account menu) and footer around every route; the signed-in user is the shared `useMe()` query (`src/lib/api.ts`). Pure sign-in logic (messages, email shape, resend cooldown) is `src/login-logic.ts`.
- The design system is Tailwind CSS v4 with tokens in `src/styles.css` (`@theme inline`); light and dark are one `light-dark()` hex value per token, and the theme button only flips `color-scheme`. Shared components (button, card, input, alert, badge, tabs, table, alert dialog) are shadcn/ui-style in `src/components/ui/`, on Radix primitives.
- `src/game/game.ts` holds the pure guess judging (`gradeIds`); the guess box is a Downshift combobox (`src/routes/play/guess-box.tsx`); `src/components/board.tsx` draws the board rows shared by Play and How to play; `src/components/theme-button.tsx` drives the theme (`src/theme.ts`).
- The roster lives in Postgres (`games`, `attributes`, `entries`, `entry_values`; migration `005_games.sql` moved Petdle in as game `petdle`). `GET /api/games/:slug` gives the page the game's attributes and active entries (`id`, `name`, `photo`); the board columns are Photo, Name, then the game's attributes. Guesses are numeric entry ids. Service seam: `src/server/games.ts` (`findGame`, `loadRoster`).
  - Attribute types: Text (exact match) and List (same set correct, shared value partially correct); grades are never stored (ADR 0013).
- Cell result classes: `correct` / `partially-correct` (arrays sharing an element) / `incorrect`, styled in `src/styles.css`.

## Daily Answer

Stored server-side per game (`daily_answers` keyed by game and date, `src/server/answers.ts`), never in the bundle (ADR 0008, 0010). Day 0 is the game's `start_date`.

- Drawn at random on the first request of a day. All missing days fill in order under an advisory lock, skipping the previous Skip Period answers (the game's `skip_period`, default 5, clamped to N-1).
- "Today" is the date in `SERVER_TIMEZONE` (default Europe/Sofia). Roster changes no longer rewrite past days.
- Migration `db/migrations/001_daily_answers.sql` backfills days 0..2026-10-16 from `db/backfill/answers.json`.

## Play

- Anonymous (`createPlay`, `src/game/play.ts`): entry ids live in `localStorage` under `game:<slug>:` keys (`createGameState`, `src/game/game-state.ts`: a missing or other-day `lastPlayed`, or a newer server `day`, clears them; blocked storage falls back to memory; the old un-prefixed keys are wiped once at start-up (`src/main.tsx`), which shows a dismissible notice that the browser guesses were reset; signing out clears every `game:*` key). `POST /api/games/:slug/grade {ids}` returns `{day, rows, victory, answer?}`, `answer` only on victory. `POST /api/games/:slug/give-up` is stateless and open to anyone by decision. Every response carries the Day Number; a client seeing a newer day resets itself (`onNewDay`).
- Signed in: email magic link (`src/server/email-login.ts`, `mailer.ts`, ADR 0011; the mail links to `${PUBLIC_URL}/verify?token=...`; client `src/routes/login-page.tsx`, `src/routes/verify-page.tsx`), Postgres sessions (`src/server/auth.ts`). `GET /api/games/:slug/state` and `POST /api/games/:slug/state/guess|give-up|merge|reset` store ids per user and day (`src/server/user-game.ts`, client `src/game/server-play.ts`); victory is derived on read. `merge` adopts leftover anonymous guesses on login (`src/game/merge.ts`).
- A draft game, or one with fewer than 2 active entries, is a 404 except to its owner and admins. `src/server/access.ts` owns that rule and the 404, 401, 403 order: `resolveGame(pool, now, req, slug, need)` with `need` = `play` | `edit` | `admin` (pure core `decide`; `resolveAdmin` for admin routes without a game). The shell, `loadGame` (play), `guardGame` (`routes/context.ts`, used by manage, answers and admin routes) all go through it, so a hidden game is a 404 before any 401/403. Signed-in game-state routes (`routes/game.ts`) still check the session first.
- Failure codes: `src/game/failures.ts` is the one table of code to HTTP status and client text (`FAILURES`, `failureText`); routes send them with `fail(res, code)` (`routes/context.ts`), `manage-client.ts` shows the text. Add a code there only.
- Limits: `src/game/limits.ts` holds every size limit (name 60, description 500, slug 3-40, attribute name 40, value 200 x 20 items, `MIN_ENTRIES`). The fields' `maxLength` values and `RESERVED_SLUGS` (every top-level page, folder and route) are tied to them by `tests/limits.test.ts`.
- Routes live in `src/server/routes/` (`auth`, `game`, `answers`, `admin`), each taking one `AppContext`.

## Admin

`/api/admin/users|backup|queue|games` and the `/admin` page (`src/routes/admin/`, tabs Users, Backups, Approval queue, All games). Answers peek/override is per game, owner or admin, in the editor's Answers tab (`src/routes/edit/answers-panel.tsx`; Answer History from a week back, real dates) over `/api/games/:slug/answers`: peek and override answers (today or future only; later generated days are re-drawn). Changing a game's skip period (0..N-1) re-draws its future generated days only (`redrawFuture`). Admin also: promote or demote users (no self or last-admin demotion), show backup age.

## Approval

`src/server/lifecycle.ts` owns every status change (edit kinds that reset approved/rejected, submit, unpublish, approve, reject) and `src/server/approval.ts` the admin queue and game list (game delete is `uploadRefs(...).dropGame`): `POST /api/games/:slug/submit` (draft or rejected, 2+ active entries, 409 `too_few_entries` / `invalid_state`) and `/unpublish` (approved) are owner/admin; `/api/admin/queue` (pending, oldest first), `POST /api/admin/games/:slug/approve|reject` (reject needs a reason, max 500) and `DELETE /api/admin/games/:slug` are admin only (Queue tab, `src/routes/admin/queue-panel.tsx`). `/api/me` gives admins `pending`, shown on the Admin link. Every transition into pending (submit, unpublish, an edit resetting approved/rejected) mails all admins through the `Mailer` (`gameLifecycle` in `lifecycle.ts`; routes pass an edit kind and cannot skip it). Pure request validators are in `src/server/validate.ts`, the shared game transaction in `src/server/tx.ts`; edits of drafts or already-pending games do not, and a mail failure never fails the edit.

## Uploads

Before upload the edit page crops each pick in a Cropper.js dialog (issue #82): photos square, covers 16:7 (`UPLOAD_SHAPES` in `src/game/crop.ts`, which also holds the sizes and 5 MB limit the server uses). `src/image-cropper.ts` is the framework-free core (decode, mount, crop to a WebP or JPEG under the limit); `src/crop-dialog.ts` is the vanilla `<dialog>` around it, so a React page only replaces the dialog. Undecodable files never reach the server. Play shows photos square (`object-fit: cover`), so older uncropped ones still line up.

`POST /api/uploads?kind=photo|cover` (signed in, raw bytes as `application/octet-stream`, 5 MB) runs `src/server/images.ts`: type by magic bytes (JPEG, PNG, WebP), sharp resize (photo 800px, cover 1200px), WebP re-encode, random-hex name in `UPLOADS_DIR` (default `./uploads`); answers `{url: "/uploads/<hex>.webp"}` or 413 `too_large`, 415 `unsupported`, 422 `corrupt`. Prod: the `uploads` named volume is rw for `api`, ro for nginx (`/uploads/`, `/api/uploads` body cap 5m). The dev server serves the same folder. Petdle's own photos were moved here once by `scripts/import-photos.mjs <photos dir> <owner email> [cover]` (`src/server/import-photos.ts`; rerunnable, skips entries already moved); the how-to-play examples live in `howto/`. Hygiene (table `uploads`): per-user rate limit (60/hour, `uploadLimit`) and byte quota (200 MB, 403 `quota_exceeded`, `src/server/upload-store.ts`). `src/server/upload-refs.ts` (`uploadRefs(pool, dir)`) owns upload references: `mayAttach(url, current, actorId, ownerId)` (clear, keep, or a file stored for the actor or the game's owner), `release(urls)` (deletes file and quota row unless a cover or entry photo, soft-deleted ones too, still uses it), `dropGame(game)`, `dropUser(id)` (delete, then release what they owned or used) and `sweep(now)` (`main.ts` at start and every 24h; files older than 1 day that nothing references). Routes never unlink files themselves; extend its reference queries when another table stores upload URLs.

## Party mode

ADR 0016. Pure rules in `src/game/party.ts` (codes, nicknames, ranking, Placement Points, the per-viewer `partyView`, socket message parsing); storage in `src/server/parties.ts` (tables from `007_parties.sql`, `sweepParties` hourly from `main.ts` and on every read of one party), actions in `src/server/party-actions.ts` (under the party row lock), the socket hub in `src/server/party-hub.ts` (`attachPartySockets(server, app)` in `app.ts` hooks it to the HTTP server; `main.ts`, `scripts/server.mjs` and the party integration test call it). HTTP: `POST /api/games/:slug/parties {nickname}` (signed in, play access) → `{code, token}`; `GET /api/parties/:code` (visitor view, also the results page); `POST /api/parties/:code/join {nickname}` → `{token}`. Socket: `/api/parties/:code/socket`, first message `hello` with the token. Client: `party.html` + `src/pages/party.ts` (`/party`, `/party?host=<slug>`, `/party/<CODE>`), `src/party-socket.ts` (reconnects), `src/party-render.ts`; the guess box and rows are shared with Play through `src/guess-board.ts`. Play shows "Host a party" on any playable game.

## Server

- Rate limits: nginx and `src/server/rate-limit.ts`. `/api/test/login` exists only with `NODE_ENV=test`.
- Migrations: `db/migrations/*.sql`, applied at startup.
- Deploy, env keys, backups: `docs/deploy.md`.

## Tests

- Unit, component and integration tests run on Vitest (`vitest.config.ts`: a `unit` project for `tests/*.test.ts`, a `ui` project for React components in `tests/ui/*.test.tsx` (jsdom, Testing Library; `npm test` runs both) and an `integration` project that runs one file at a time). `tsc -p tsconfig.test.json` type-checks them first. Assertions use `node:assert/strict`.
- `npm run test:integration` runs the HTTP API against Testcontainers Postgres (needs Docker).
- Page URLs are served by `scripts/server.mjs` (dev) and `location /` `try_files` in `deploy/nginx.conf` (prod); `tests/e2e/server.spec.ts` and `tests/build-wiring.test.ts` cover both lists.
- `npm run test:e2e` starts a Testcontainers Postgres and Mailpit via `tests/e2e/serve.ts` (needs Docker); sign-in mail is read back through Mailpit's API. One integration test delivers through real nodemailer to Mailpit. The Daily Answer is random there; tests learn it through the API.
